# План реализации платформы "Живое знание"

Этот план разбивает запуск системы на независимые потоки работ, минимизируя конфликты между командами. Он строится на архитектурных принципах из README: атомарность, иерархичность и связность знаний, а также предполагает стек из PostgreSQL+pg_vector, FastAPI, LangChain, SentenceTransformers и фронтенда на современном SPA-фреймворке.

## Поток A. Фундамент инфраструктуры

1. **Развертывание окружений**
   - Подготовить Docker Compose с сервисами PostgreSQL (включая расширение `pgvector`), бекенда и фронтенда.
   - Настроить базовые переменные окружения (LLM API, пути к моделям SentenceTransformers, параметры подключения к БД).
2. **CI/CD и качество**
   - Настроить линтеры (ruff, mypy) и форматеры (black) для Python, ESLint/Prettier для фронтенда.
   - Включить в pipeline запуск тестов и проверку миграций.
3. **Наблюдаемость**
   - Подключить базовый логгер (структурированные логи) и трейсинг (OpenTelemetry + Jaeger) на уровне FastAPI.

## Поток B. Домен данных и миграции

1. **Базовые сущности**
   - Реализовать миграции Alembic для таблиц `artifacts`, `messages`, `structured_entries`, `schemas`, `links` в соответствии с моделью данных README.
   - Добавить индексы по векторным и внешним ключам.
2. **ORM-слой**
   - Создать модели SQLModel, отражающие таблицы, и Pydantic-схемы для API.
   - Обеспечить фабрики для создания связей родитель/ребенок и knowledge graph.
3. **Репозитории и Unit-тесты**
   - Реализовать слой репозиториев с чистыми интерфейсами (Hexagonal architecture).
   - Написать тесты с использованием in-memory PostgreSQL (например, testcontainers) для проверки CRUD и запросов близости по векторам.

## Поток C. AI-ядро и сервисы интеллекта

1. **Сервис эмбеддингов**
   - Обернуть SentenceTransformers в отдельный сервис/адаптер с асинхронным API и кешированием.
2. **Навигатор контекста**
   - Реализовать компонент, который принимает сообщение, вызывает эмбеддинг-сервис и ищет релевантные `artifacts`, `structured_entries`, `schemas`.
   - Покрыть тестами на синтетических данных (TDD с фикстурами).
3. **Генератор структур и оркестратор**
   - Настроить LangChain-цепочки: извлечение новых схем, обновление summary, предложение связей.
   - Обеспечить конфигурируемость промптов, покрыть интеграционными тестами с заглушкой LLM.

## Поток D. Бекенд-API (FastAPI)

1. **Скелет приложения**
   - Создать модуль FastAPI с разделением на роутеры (artifacts, messages, schemas, links).
   - Настроить DI контейнер для репозиториев и AI-сервисов.
2. **Реализация эндпоинтов**
   - `POST /chat/message`: прием сообщений, вызов Навигатора и Оркестратора, запись результатов.
   - `GET /artifacts/{id}`: получение артефакта с вложенными сообщениями и структурированными записями.
   - `POST /artifacts/{id}/links`: создание связей knowledge graph.
3. **WebSocket-канал**
   - Реализовать двусторонний канал для чата, интегрировав в него результаты AI-ядра.
4. **Тестирование**
   - Покрыть API e2e-тестами (pytest + httpx + тестовый Postgres).

## Поток E. Фронтенд (SPA)

1. **Скелет приложения**
   - Настроить проект (React/Vue/Svelte), подключить менеджер состояния, дизайн-систему.
2. **Основные экраны**
   - Дашборд артефактов, чат артефакта (с ветками), просмотр structured entries, визуализация связей (graph view).
3. **Интеграция с API**
   - Подключение к WebSocket чата, отображение ответов и предложений AI.
   - Формы для создания связей, новых артефактов, применения схем.
4. **Тестирование**
   - Написать компонентные тесты (Vitest/Jest) и e2e (Playwright/Cypress).

## Поток F. Дополнительная ценность и эксплуатация

1. **Автоматизация шаблонов**
   - Реализовать фоновый воркер, который периодически анализирует активность и предлагает готовые схемы для новых артефактов.
2. **Распределение нагрузки**
   - Внедрить кеширование для часто запрашиваемых артефактов, рассмотреть очереди (RabbitMQ/Redis) для долгих AI-операций.
3. **Обратная связь и аналитика**
   - Добавить сбор метрик использования (кто создает артефакты, какие связи популярны), настроить дешборды.

## Порядок запуска

1. Запустить поток A (инфраструктура) параллельно с началом потока B.
2. После готовности ORM и репозиториев (поток B) стартовать поток C и D.
3. Поток E подключается, когда базовые API стабилизированы.
4. Поток F выполняется последовательно после выкатки MVP.

Такое разбиение позволяет командам работать параллельно без конфликтов и поэтапно раскрывает архитектуру "Живого знания".
