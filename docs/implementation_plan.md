# План развития "Живого знания": параллельные потоки

Базовый каркас (слои API/Service/Repository, миграции, тестовый контур, конфигурация) завершен. Следующий этап направлен на внедрение интеллектуальных функций. Чтобы команде было проще двигаться без конфликтов слияния, задачи сведены в независимые потоки с четкими интерфейсами.

## Поток A. Векторная инфраструктура

**Зона ответственности:** подготовить единый слой доступа к эмбеддингам и векторному поиску.

1. Реализовать адаптер `PGVectorIndex`, совместимый с текущим протоколом `VectorIndex`, с поддержкой фильтров по типу сущности и стратегий дистанций (`cosine_distance`/`l2_distance`).
2. Перевести репозитории на async-сессии SQLModel/SQLAlchemy, добавить внедрение зависимостей через `Depends` вместо ручного создания.
3. Интегрировать `VLLMEmbeddingClient` в операции создания/обновления артефактов, сообщений и структурированных записей, обеспечив пересчет вектора при изменении summary или структуры.
4. Обновить миграции: заменить индексы `ivfflat` на `hnsw`, добавить процедуру переиндексации существующих данных и конфигурируемые параметры (`m`, `ef_construction`).

**Интеграционный контракт:** предоставить сервисам метод `search(query, *, entity_types)` и гарантировать заполненность векторных полей после операций записи.

## Поток B. Контекстная навигация

**Предпосылка:** поток A завершил `PGVectorIndex` и обновил репозитории.

1. Расширить `ContextNavigator`, используя новый индекс для поиска в иерархии артефакт → сообщение → structured entry.
2. Ввести конфигурируемые пороги принятия решений (>90% — продолжить, 70-90% — уточнить, <70% — создать новое) и сохранять принятое решение для explainability.
3. Добавить модульные тесты, покрывающие сценарии выбора артефакта/создания новой ветки с использованием моков индекса.

**Интеграционный контракт:** предоставить оркестратору структуру результата вида `{decision, target, evidence}` без записи в базу.

## Поток C. Оркестратор знаний

**Предпосылка:** потоки A и B готовы.

1. Расширить `KnowledgeOrchestrator.respond`, чтобы потреблять решения навигатора, запускать LLM и принимать действия (обновление summary, создание structured entry, формирование предложения пользователю).
2. Добавить второй LLM-вызов или function calling для анализа ответа и выбора операций над базой знаний.
3. Реализовать автоматическое обновление `summary`, создание `structured_entries` и рекомендации по связям, используя существующие репозитории.
4. Расширить unit/E2E-тесты, покрыв сценарии автоматических действий с моками LLM и репозиториев.

**Интеграционный контракт:** публиковать в шину событий (или лог) решения оркестратора для последующей аналитики.

## Поток D. Обучение на примерах

**Предпосылка:** поток C предоставляет события об ответах и контексте.

1. Создать `SchemaLearningService`, анализирующий новые сообщения и предлагающий JSON Schema для повторяющихся структур (ключ: значение, чек-листы и т.п.).
2. Подключить сервис к оркестратору: выдавать пользователю предложение, обрабатывать подтверждение/отказ, создавать связанные `structured_entries`.
3. Добавить тесты на распознавание паттернов и корректное взаимодействие с оркестратором.

**Интеграционный контракт:** возвращать в оркестратор `{schema, confidence, suggested_fields}` и уметь обновлять схемы без изменения существующих данных.

## Поток E. Наблюдаемость и эксплуатация

**Можно выполнять параллельно с потоками B-D.**

1. Логировать метрики порогов сходства, принятых решений и действий оркестратора; интегрировать с Prometheus/OpenTelemetry.
2. Реализовать фоновые задачи переиндексации эмбеддингов и оповещений о деградации качества поиска.
3. Подготовить дешборды и алерты, используя данные, публикуемые оркестратором и сервисами.

## Координация

1. Поток A запускается первым и предоставляет контракт для остальных.
2. Потоки B и E могут стартовать сразу после A; конфликтов в коде не ожидается при соблюдении контрактов.
3. Поток C опирается на результаты B и данные A; поток D зависит от событий C.
4. Регулярные синки между лидами потоков фиксируют изменения контрактов, чтобы избежать конфликтов слияния.

Такой разрез позволяет командам работать параллельно, сохраняя единый фокус на превращении системы в самоорганизующееся хранилище знаний.
